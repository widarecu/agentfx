# v0.6.1 Paper Trading — Live Execution & Observability

## Context

**Why now.** v0.6.0 shipped the paper-trading UX end-to-end — approval queue, per-user OANDA credentials, RBAC isolation, kill switch, live-equity chart, run-detail page. But the 24-hour UAT smoke-test on 2026-07-08 exposed a critical gap: **the runner doesn't actually trade**. `src/agentfx/services/paper_runner.py::_execute_loop` only polls balance + risk gates every 5 seconds. It never fetches candles, never compiles the DSL, never calls `place_market_order`. Confirmed by `grep -n "generate_signals\|place_market_order\|StrategySpec" src/agentfx/services/paper_runner.py` returning no matches. Wilson's real run (`run_1783513720844_paper_EUR_USD_M1_ba51b53bd3`) sat RUNNING for 24 hours with zero trades and unchanged balance before being halted on 2026-07-09 with `stop_reason='USER_KILL_v0.6.0_gap'`.

**Every other v0.6.1 backlog item presupposes the runner is executing.** The trades endpoint returns nothing until trades are persisted. The decision-log stream is empty because the runner never logs signal decisions. The backtest overlay is meaningless without a live curve to overlay against. Validator write-back matters only if there are validated genomes to deploy. So v0.6.1 is not "polish + one bug fix" — it is a coherent live-execution sprint where the runner change unblocks everything downstream.

**Why this shape.** The plan is deliberately narrower than v0.6.0. No new UX design pass — the /paper/:id page already has the placeholders (Trades table, Decision log). No new pages. No schema-level surgery — the `runs / orders / trades / decision_logs` tables all exist from PR-F. The work is: (i) fix the runner to actually run the strategy, (ii) surface what the runner writes via three thin GET endpoints, (iii) wire the endpoints into the existing frontend placeholders, (iv) close the validator write-back bug so the approval queue populates from real evolutions instead of manual SQL. Everything else — LLM naming, notifications, streaming pricing — is v0.6.2 or later.

**Intended outcome.** In ~1 week, ship v0.6.1 such that a TRADER user can:
1. Have their VALIDATED genomes appear automatically in the approval queue (no manual `UPDATE`).
2. Approve a genome and watch actual OANDA Practice orders show up in the OANDA dashboard within one granularity tick.
3. See trades stream into the run-detail Trades table with signal-reason + origin badges.
4. See gate refusals / orders / kills stream into the Decision log as they happen.
5. Reload the /paper/:id page after 30 minutes and see the full accumulated equity curve, not a fresh window.
6. See the backtest OOS equity overlay drawn from real walk-forward data, not the placeholder curve.

## User-approved decisions (locking these before Phase 1)

Recommendations pre-selected; flag any you want changed before I start on PR-A.

| # | Decision | Recommendation | Rationale |
|---|---|---|---|
| 1 | **Candle staleness policy** — what does the runner do when the latest candle is older than granularity × 2? | **Skip signal evaluation, log a warning, keep polling.** Do not halt. | Ingestion outages (OANDA maintenance, weekend gaps, the app-wide ingester falling behind) are common and non-fatal to strategy correctness. Halting on staleness turns every ingestion hiccup into a paper-run failure; skipping lets the runner resume the moment fresh data arrives. Kill-switch and daily-loss halts remain the hard-stop mechanisms. |
| 2 | **Loop cadence architecture** — how do we run 5s health polling and slower signal polling together? | **One subprocess, two internal timers.** Health tick every 5s (balance, kill flag, gates). Signal tick aligned to the granularity — M1 = every 60s aligned to `:00`, H1 = every 3600s aligned to `HH:00`. | Two subprocesses would double the `OandaClient` connection count per run, complicate credential loading, and require inter-process coordination for the risk-config shared state. A single loop with `next_signal_at = align_to_granularity(now)` is simpler and matches how `evolution_runner.py` structures its work. |
| 3 | **OANDA v20 pricing stream** — subscribe to the streaming pricing endpoint, or keep polling? | **Defer streaming to v0.6.2.** Keep polling `get_pricing` on the signal tick. | 60s cadence on M1 is fine for validation of the execution path. Streaming is a latency optimization, not a correctness requirement. Introducing WebSocket lifecycle management alongside the runner rewrite doubles the surface area of what can go wrong in the sprint. |
| 4 | **Order placement timing** — place orders at candle close, or intra-bar? | **Candle close only.** The signal tick runs immediately after the granularity boundary; the runner evaluates the closed bar, then places any resulting order. | Matches the backtest engine's assumption (signals fire at bar close). Any intra-bar entry would drift live behavior away from validated backtest behavior — the exact scenario Wilson called out on 2026-07-08 as the reason paper matters at all. |
| 5 | **Position management on signal flip** — how do we go from long to short (or vice versa) in one tick? | **Two-step: close current position, then place new order.** OANDA v2 supports net position but the two-step is explicit in the decision log and easier to reason about in the trades table. | The `decide_action` helper (already in `paper_runner.py`) returns `close` OR `place` per tick; we run through one full tick to close, then the next signal-tick's evaluation picks up the flip. Simpler audit trail; consistent with what the backtest engine records. |
| 6 | **Stop-loss / take-profit sourcing** — where do SL/TP values come from? | **`run.risk_config.stop_loss_pips` / `run.risk_config.take_profit_pips` when set; otherwise no broker-side SL/TP.** Daily-loss and kill-switch remain the safety net. | The genome DSL doesn't universally carry SL/TP (it's a signal-generation language). Risk config on the run row is user-tunable at deploy time via the existing DeployPaperModal (add two optional fields there). Absent values means the strategy exits on signal reversal only — same as backtest. |
| 7 | **Scope discipline — what's IN v0.6.1?** | **IN:** live DSL execution in runner, trades endpoint, decisions endpoint, equity persistence + endpoint, backtest overlay endpoint, validator write-back fix, DeployPaperModal SL/TP fields. **OUT:** LLM-suggested deployment name, notifications, streaming pricing. | If all seven IN items land, the paper platform is genuinely usable for real strategy evaluation. LLM naming is a nice-to-have that adds latency to deploy modal open; notifications need a delivery-channel design; streaming needs its own PR. All three fit v0.6.2 cleanly. |

## Milestone scope (locked, contingent on the table above)

**Exit criteria** — all six must be true before v0.6.1 is merged to main:
1. A validated genome from a real evolution run appears in `/paper/approvals` without any manual DB writes (US-021 write-back closed).
2. `paper_runner._execute_loop` fetches candles → compiles DSL → generates signals → places orders → persists trades on real OANDA Practice, verified by a fake-OANDA integration test.
3. `/paper/:id` Trades table populates from `GET /paper-runs/{id}/trades` — entry timestamp, exit timestamp, side, quantity, pnl, origin (live/backtest), signal reason.
4. `/paper/:id` Decision log streams `USER_KILL`, order placement, gate refusals, and `USER_DEPLOY_PAPER` entries via `GET /paper-runs/{id}/decisions` with 5s polling.
5. LivePnLChart survives a browser reload — equity samples are persisted to a new `paper_equity_snapshots` table on every signal tick, and `GET /paper-runs/{id}/equity` returns the full history.
6. LivePnLChart's backtest overlay curve is real walk-forward OOS equity fetched from `GET /paper-runs/{id}/backtest-overlay`, not the placeholder.

### PR-B (Day 2–3, medium) — Runner signal loop

The centerpiece. Rewrite `_execute_loop` to run two interleaved cadences in one subprocess:

```
loop forever:
  now = time.now()

  # Health tick — always
  reload run row; if kill_requested_at set → _flatten_and_halt(USER_KILL); return
  balance = client.get_account_balance()
  update run.current_balance, run.pnl
  gate = evaluate_all(risk_state, proposed_units)
  if gate refuses with DAILY_LOSS_LIMIT / BROKER_CIRCUIT → _flatten_and_halt(reason); return

  # Signal tick — only at granularity boundaries
  if now >= next_signal_at:
    next_signal_at = align_to_granularity(now + granularity_seconds)
    candles = fetch_recent_candles(instrument, granularity, bars=strategy.min_lookback + 50)
    if latest_candle_timestamp < now - 2 * granularity_seconds:
      log USER_SIGNAL_SKIPPED_STALE, continue
    signals = strategy.generate_signals(candles_df)
    last_signal = signals.iloc[-1]
    position = client.get_position(instrument)
    action = decide_action(last_signal.direction, last_signal.units, position.net_units)
    if action.kind == 'place':
      order = client.place_market_order(instrument, action.signed_units, stop_loss_pips, take_profit_pips)
      persist Trade row (entry_timestamp, entry_price, quantity, side, run_id, signal_reason=last_signal.reason)
      write USER_ORDER_PLACED decision log
    elif action.kind == 'close':
      result = client.close_all_positions(instrument)
      update matching open Trade row (exit_timestamp, exit_price, pnl, pnl_pct)
      write USER_POSITION_CLOSED decision log

    # Snapshot equity for the reloadable chart
    persist PaperEquitySnapshot(run_id, timestamp=now, balance, unrealized_pnl)

  sleep(min(5, seconds_until(next_signal_at)))
```

Key design decisions:
- `align_to_granularity(t)` rounds up to the next boundary in UTC. For M1 that's `ceil(t / 60) * 60`; for H1 that's the next `HH:00`. Prevents drift from accumulating over long runs.
- `strategy.min_lookback` comes from the compiled DSL — take the max of every indicator's lookback (SMA_50 needs 50, MACD_26 needs 26, etc.) and add a 50-bar safety margin so early-bar NaNs from indicators don't cause NaN signals.
- The two-timer split means a stuck signal evaluation (network hang) can still time out to the health tick's 5-second cadence — the kill switch responds in <5s even mid-signal-tick. Signal work runs on the same thread but wrapped in `contextlib.timeout(30)`.
- SL/TP: read `run.risk_config.get('stop_loss_pips')` / `.get('take_profit_pips')`; pass to `client.place_market_order` if set, otherwise None.

## Phase 3 — Read endpoints + DeployPaperModal fields (Day 5–6)

### PR-D (Day 5, medium) — Trades / decisions / equity endpoints

All under `/api/v1/paper-runs/{id}/`, all RBAC-scoped via `scope_query_to_user`. Payloads:

- `GET /trades` → `[{id, entry_timestamp, exit_timestamp, side, quantity, entry_price, exit_price, pnl, pnl_pct, origin, signal_reason}]`. Ordered newest-first. Paginated `?limit=100&offset=0`. `origin` is always `live` in v0.6.1 (the backtest overlay comes from a separate endpoint); the field exists for v0.7.0 forward-portability.
- `GET /decisions` → `[{id, timestamp, action_type, actor_user_id, reason, metadata_json}]`. Ordered newest-first. Filter to the 6 action types the runner emits + the 4 user actions (`USER_DEPLOY_PAPER`, `USER_APPROVE_GENOME`, `USER_REJECT_GENOME`, `USER_KILL_PAPER`).
- `GET /equity` → `[{timestamp, balance, unrealized_pnl}]`. Full history since run start. Paginated by time window `?from=&to=` so the chart can render a fixed window; default = all.

Alembic migration adds `paper_equity_snapshots`:
- `id` UUID PK
- `run_id` VARCHAR FK → `runs.id`
- `timestamp` TIMESTAMP NOT NULL
- `balance` DECIMAL(18,2) NOT NULL
- `unrealized_pnl` DECIMAL(18,2) NOT NULL
- Index on `(run_id, timestamp)`

### PR-E (Day 5, small) — Backtest overlay endpoint

`GET /paper-runs/{id}/backtest-overlay` → `[{timestamp_relative_seconds, balance}]`. Fetches the paper run's `strategy_genome_id`, walks back to the `evolution_run` that produced it, pulls the OOS equity time series from the champion-by-OOS fold's persisted results, normalizes timestamps to seconds-since-run-start so the frontend can render it against the LivePnLChart's relative x-axis directly. Handles the "no OOS equity persisted" case by returning `[]` with a 200; frontend shows a "backtest curve unavailable" note.

## Open questions to resolve during Phase 2

Not blockers for planning-doc approval, but worth surfacing so they don't slow PR-B:

- **Timeout on `strategy.generate_signals`** — if the compiled DSL hangs on a bad input (NaN candles, exotic indicator combination), 30s is a defensive ceiling. Is that the right value, or do we want it tighter (5s) so a slow strategy can't starve the health tick? Recommend 30s for MVP, revisit if we see starvation in UAT.
- **Decision log volume** — 5 action types × one signal tick per minute × 24h × 30 days = ~215k rows per run for a busy strategy. The `decision_logs` table already has a `run_id` index but no partitioning. Not urgent, but worth a note in the v0.7.0 backlog.
- **Position sizing when balance changes** — `decide_action` currently uses `max_position_size_units` from risk_config as an upper bound. Should the actual sized units scale with balance (Kelly-style), or stay fixed? Fixed matches the backtest engine's default; leave scaling for v0.7.0 risk-config revamp.
