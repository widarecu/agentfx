## Section 1 — Rebuild + migrate the UAT container

**Purpose:** advance the UAT backend to include every v0.6.1 change (new migrations, new endpoints, new runner code).

- [ ] From the repo root, rebuild the UAT backend image and recreate the container:
      ```bash
      docker compose --profile uat up -d --build backend-uat
      ```
      The `backend-uat` service's entrypoint runs `alembic upgrade head` on start, so no separate migrate step is needed. Watch the logs briefly to catch any error:
      ```bash
      docker compose --profile uat logs -f backend-uat | head -60
      ```
- [ ] Confirm the migration head is `7d1a8f4c9e63` (paper_equity_snapshots):
      ```bash
      docker compose --profile uat exec -T backend-uat alembic current
      ```
      Expected output ends with `7d1a8f4c9e63 (head)`. If it shows an earlier revision, the container image didn't rebuild — force it:
      ```bash
      docker compose --profile uat build --no-cache backend-uat
      docker compose --profile uat up -d backend-uat
      ```
- [ ] Verify the volume wasn't wiped. Quick smoke check — pre-existing evolution runs should still be there:
      ```bash
      docker compose --profile uat exec -T postgres-uat psql -U uat_user -d agentfx_uat \
        -c "SELECT COUNT(*) FROM evolution_runs;"
      ```
      Expected: at least 17 (the count from the 2026-07-08 audit). If it says 0 or a much smaller number, **STOP** — the volume was replaced and Wilson's OANDA data is gone. Do not proceed; investigate before doing anything else.

## Section 2 — Fresh evolution + validator write-back proof

**Purpose:** confirm US-027's diagnostic banner tells the truth. Even if no genome passes Gate B on this evolution (which is likely given prior 0/17 pass rate), the empty-state banner should now explain *why* instead of just being blank.

- [ ] Trigger a new evolution run on UAT via `/evolution/new` in the portal. Keep the parameters small so it completes in <10 min (e.g. instrument=EUR_USD, granularity=M15, 3 folds, 8 generations, top_n_to_validate=10).
- [ ] Wait for the run to complete. Confirm the validator wrote back real verdicts by counting non-null `validator_passed` rows for that run's genomes:
      ```bash
      docker compose --profile uat exec -T postgres-uat psql -U uat_user -d agentfx_uat \
        -c "SELECT validator_passed, COUNT(*) FROM strategy_genomes sg \
            JOIN generations g ON g.id = sg.generation_id \
            JOIN evolution_runs er ON er.id = g.run_id \
            WHERE er.id = '<paste-run-id-here>' \
            GROUP BY validator_passed;"
      ```
      Expected: at least one non-null row (probably `false` — that's the training/OOS gap, not a bug). If every row is NULL, US-027's premise (write-back works) is wrong — file a bug and stop.
- [ ] Open `/paper/approvals` on the UAT portal. Two acceptable outcomes:
  - **The empty-state banner reads** `"N evolution runs · M genomes validated · 0 passed Gate B. Closest to passing: [genome_id]"` with a card linking to the near-miss. This is the US-027 diagnostic in action — screenshot it as evidence.
  - Or the queue has one or more deployable rows if this evolution actually produced a passing genome (rare but possible). Screenshot the queue.

## Section 3 — ADMIN override → approve → real OANDA order

**Purpose:** end-to-end proof that the runner places a real order on OANDA Practice.

- [ ] If the queue was empty in step 2, click the "Closest to passing" card → GenomeDetail → **Override validator verdict** (ADMIN-only button, only visible if Wilson is logged in as an ADMIN user). Set `new_value=true`, reason (min 20 chars): `"UAT verification for v0.6.1 runbook — closest-to-passing genome unblocked for smoke test."`. Confirm.
- [ ] `/paper/approvals` should now show the genome. Click **Approve**.
- [ ] In the DeployPaperModal:
  - Verify the OANDA sub-account picker lists at least one account.
  - Set `max_position_size_units = 10_000` (1 standard lot).
  - Set `daily_loss_pct = 2.0`.
  - **Test the US-028 SL/TP fields:** expand "Advanced risk controls", set `Stop loss = 20`, `Take profit = 40`. Confirm the input accepts both.
  - Click Approve & deploy.
- [ ] Watch the run detail page load. Status should transition `APPROVED → RUNNING` within one or two seconds.
- [ ] Wait for the next M1 boundary (max 60 seconds). An order should appear:
  - **On the OANDA Practice dashboard** — a filled trade with SL/TP levels visible.
  - **On the `/paper/:id` Trades table** — one row, `side=LONG`, `origin=live`, `signal_reason` populated (e.g. `"sma > sma"`), `Exit` column shows "open".
  - **On the Decision log** — a `USER_ORDER_PLACED` entry with instrument + fill price in the reason text.
- [ ] Cross-check the `broker_trade_id`. In the Decision log entry, click to expand → `outputs_json.broker_trade_id` should match the trade ID OANDA shows on its dashboard. This is the definitive proof the runner is really talking to OANDA and not to a mock left in the code path somewhere.

If any of the above doesn't fire within ~3 minutes: check `docker compose --profile uat logs -f backend-uat` for exceptions in the paper runner subprocess. Common failure modes:
- Stale candles → look for `USER_SIGNAL_SKIPPED_STALE` in the DecisionLog. Ingestion may be behind; wait for it to catch up.
- OANDA HTTP 401 → credentials invalid. Re-verify in `/settings`.
- Compilation error on the deployed genome's DSL → runner logs will show the traceback. That's a bug — file it.

## Section 5 — Kill switch verification

**Purpose:** confirm the sub-5s kill guarantee still holds after the runner rewrite.

- [ ] Click the red kill switch button at the top-right of `/paper/:id`. Note the wall-clock time.
- [ ] The 3-second undo toast appears. Let it expire (don't click Undo).
- [ ] Within 5 seconds of the toast expiring:
  - The status pill should flip to `HALTED_MANUAL`.
  - Any open OANDA position on this instrument should be closed (verify on the OANDA dashboard).
  - The Decision log should show a `USER_KILL_PAPER` entry.
  - The Trades table's open row should transition to closed with exit price + pnl populated.

If more than 5 seconds elapse, that's a regression from v0.6.0 — file a bug.

**Purpose:** catch bugs that only surface over time (OANDA rate limits, ingestion gaps, timezone edges, memory leaks).

- [ ] Note the start time (wall clock and `run.started_at`).
- [ ] After 24 hours, spot-check:
  - Runner subprocess is still alive: `docker compose --profile uat exec -T backend-uat ps aux | grep paper_runner`.
  - `runs.updated_at` is within the last few minutes (health tick is firing).
  - `paper_equity_snapshots` count is roughly (elapsed_minutes / granularity_minutes).
  - The frontend chart is still current.
- [ ] After 48 hours, evaluate against the success criteria in section 7.

If the runner crashes during observation, the watchdog should flip the run to `ERROR` with `stop_reason='process_crashed'`. That's the specific failure mode we want visibility on — if it happens, capture the backend logs:
```bash
docker compose --profile uat logs backend-uat --since 60m > runner-crash-$(date +%s).log
```

## Rollback plan

If a critical bug surfaces during sections 3-6 and you need to unwind:

**Code rollback:**
```bash
git revert 021f1e1 4813f5f 7b4d928 32b1d2d 8e62f69
git push origin main
docker compose --profile uat up -d --build backend-uat
```
This restores the pre-v0.6.1 backend behavior. `alembic upgrade head` inside the rebuilt container will notice the migrations are already applied and no-op. To also downgrade the migrations:
```bash
docker compose --profile uat exec -T backend-uat alembic downgrade 9a2f4b8c3e17
```
This drops `paper_equity_snapshots` and removes the `origin` / `signal_reason` columns on `trades`. Both migrations use `ondelete=CASCADE` / are safely nullable, so no orphan data is created and no existing rows are corrupted.

**Data preservation:** the UAT volume (`postgres_uat_data`) is preserved through any container rebuild — the rollback affects only the backend image + schema. Wilson's real OANDA candles + user account survive.

**What NOT to do during rollback:**
- Do not run `docker compose down -v` on the UAT profile — the `-v` flag wipes the volume.
- Do not run `make e2e` at any point — it wipes the `test` volume, and if the `PROFILE` guard were ever bypassed it would wipe UAT too.
- Do not delete any evolution runs to "clean up" — they're evidence of what actually happened during smoke-test.

## When to re-run this runbook

- Before every subsequent v0.6.x tag (any change touching runner / paper endpoints / DeployPaperModal).
- After any change to the migrations under `migrations/versions/` that touches paper-trading tables.
- If a paper runner subprocess ever exits with a `stop_reason` other than `USER_KILL` / `COMPLETED` on UAT — treat as a regression signal, re-do sections 3-6.
